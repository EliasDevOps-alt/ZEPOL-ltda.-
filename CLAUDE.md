# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo (`e:\ZEPOL`) is a single git repository (root here, not per-subfolder) containing:

- `For_contro_mp v.1.xlsx` / `Sin título.xlsm` — the original Excel/VBA raw-material control system used by ZEPOL Ltda. (a flexible-packaging plant: printing, lamination, extrusion, slitting, pouching). These are the source of truth for the business rules the new system replaces; keep them for reference, don't edit them.
- `OC 2025 bas.xlsx` — a **separate, still-actively-used** Excel workbook with a sheet called "oc mp" where the client registers new órdenes (cliente, datos comerciales, up to 6 materiales — no proceso/máquina). It *can* be password-protected (`EXCEL_OC_MP_PASSWORD` / the password saved in `configuracion`, see below) but doesn't have to be — the client removed the password at one point ("no quiere contraseñas en la hoja de Excel"), and `excel_oc_mp.py` has to handle both. The client explicitly does **not** want to migrate off this workbook — `sistema-mp` reads from it live and can save an OT from it into the database, but nothing here should assume Excel goes away. See "Excel OC-MP integration" below.
- `sistema-mp/` — the replacement desktop system being built: a FastAPI backend + an Electron/React desktop client, sharing one PostgreSQL database, meant to run on a machine on the plant's LAN that the other station PCs connect to.
- `sistema-mp/INSTALACION_SERVIDOR.md` — the step-by-step runbook for installing the server (planta baja): SSH, Python/PostgreSQL/Git, cloning, restoring a real DB dump, first `uvicorn` run, the Task Scheduler + firewall setup, connecting the Excel share, and publishing app updates. Written for a non-technical operator following it live over several sessions — keep it in sync with any change to the deploy story (new dependency, new required firewall rule, new env var) rather than letting it drift. See "Deployment topology and auto-update" below for the concepts behind it.

Remote: `origin` → `https://github.com/EliasDevOps-alt/ZEPOL-ltda.-.git` (`main`, pushed).

## Commands

### Backend (`sistema-mp/backend`)

```
.venv\Scripts\activate
uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

- Venv uses **Python 3.12** (`py -3.12 -m venv .venv`), not the system's Python 3.8 — the codebase relies on syntax that only works reliably under 3.10+.
- DB connection, JWT secret, and `EXCEL_OC_MP_PASSWORD` come from `.env` (see `.env.example`); `database.py` calls `load_dotenv()` automatically.
- No test suite or migration tool (Alembic is installed but unused) exists yet — schema changes are applied by hand against `db/schema.sql`.
- Set/reset a user's login password: `python scripts/set_password.py <INICIAL>` (e.g. `ER` for Erasmo).
- **`--reload` sometimes doesn't fully pick up model/schema changes** — has happened repeatedly (uvicorn's WatchFiles reloader logs "Reloading..." but the worker process keeps serving stale code, especially after editing `models.py`/`schemas.py`, but also seen after adding a brand-new route to a `views/*_view.py` — a new endpoint returning a bare "Not Found" with no custom detail message, instead of a domain 404, is the tell that the route genuinely isn't registered in the running process yet, not that something's wrong with the route itself). If a change doesn't seem to take effect, don't trust `--reload`: kill the whole process tree (reloader **and** its child worker, `taskkill /PID <reloader> /T /F`) and start a fresh `uvicorn ... --reload` instead of assuming the code is wrong. Verify with `GET /openapi.json` (check the field/route actually shows up) before telling the user it's fixed. Check `tasklist //FI "IMAGENAME eq python.exe"` for **more than one** leftover reloader+worker pair before restarting — across a long session it's easy to end up with several stacked from earlier restarts that never got cleaned up; kill all of them, not just the newest. Separately: `taskkill /T` on the backend's process tree does **not** reliably kill an `EXCEL.EXE` that `escribir_oc_mp` launched via COM — COM-activated processes aren't children in the OS process tree, so a force-killed backend can leave Excel running (and, worse, orphaned mid-`Save()`) — see the Excel OC-MP gotcha below for why that matters.
- When testing entrega/devolución features against real (throwaway) data, creating the `OtProceso`/`OtMaterial` rows directly with `psql` instead of going through `POST /ordenes-trabajo/detalle` is much faster and avoids the Excel COM write-back (`escribir_oc_mp`) entirely — going through the real Crear-OT flow triggers a live COM `Save()` against whatever `ruta_excel_oc_mp` currently points to, which is slow (COM contention with a real Excel session can take 30–60s+) and, per the gotcha below, risks corrupting that file if interrupted. Always clean up (`DELETE`) any throwaway rows/users afterward.
- **Calling `ordenes_controller` functions directly from a Python script (bypassing HTTP, to test/inspect quickly) still triggers `_sincronizar_excel`/`escribir_oc_mp` exactly like going through the real app would** — `guardar_detalle`, `actualizar_pendiente`, `eliminar_pendiente`, promoting a pendiente, etc. all call it. In practice this reliably leaves an orphaned `EXCEL.EXE` behind on close/quit (see the COM gotcha below — happened on essentially every such script call in one session, even against a small scratch workbook), so after any direct-script test that touches one of these, check `tasklist //FI "IMAGENAME eq EXCEL.EXE"` and `taskkill //F //IM EXCEL.EXE` before moving on, the same as you'd do after a real app write. A "sincronizado_excel: False" result from a script like this can be a false negative from the close/quit step failing *after* the write already succeeded — verify the actual file content (`openpyxl`, read-only) before assuming the write itself failed.

### Database

- `db/schema.sql` — full DDL, the source of truth for the schema. Run it against a fresh `zepol_mp` database with `psql -U zepol -d zepol_mp -h localhost -f db/schema.sql`.
- `db/seed_master_data.sql` — master data extracted from the original Excel (procesos, máquinas, estados_sid — now 6 values including `COMPLETADO`, usuarios, and the 564+ rows of `materiales`, including the 3 `es_tinta` ink-charge rows).
- There is no migration tool wired up. When `models.py` and `schema.sql` diverge, changes are applied to the live DB by hand with `ALTER`/`DROP`+recreate via `psql`, then both files are kept in sync manually.
- **Gotcha that has already caused a real bug**: `vista_consumo` is a SQL `VIEW`. Editing its `CREATE VIEW` text in `schema.sql` does **not** change the live database — Postgres won't let you `ALTER` a view's column list, so the live view has to be explicitly `DROP VIEW` + recreated from the updated SQL every time its definition changes, or every consumer (`consumo_controller`, anything doing `SELECT *` from it) breaks with a Pydantic "field required" 500 the next time a field is added. Regression-test `GET /consumo` after any schema change that touches this view. It currently exposes: `ot_material_id, numero_ot, cliente, diseno, proceso, proceso_id, maquina, maquina_id, material_id, codigo_mp, descripcion, unidad, es_tinta, usa_bobinas, estado_sid, sid_devolucion_completado, es_materia_prima, insumo_de_codigo_mp, tiene_materia_prima, cantidad_requerida, total_entregado, total_devuelto, total_ingresado, consumo_neto, material_sustituido`. Note `insumo_de_codigo_mp` is a `COALESCE` over two parents — the pedido it completes (`insumo_de_id`) *or* the still-unassigned pendiente (`insumo_de_pendiente_id`)..
- Two tables exist purely to support the Excel integration and aren't part of the original domain model — see "Excel OC-MP integration" below: `configuracion` (generic key/value settings, currently just the Excel file path) and `ot_materiales_pendientes` (materials awaiting proceso/máquina assignment).
- **The server runs PostgreSQL 18, the dev laptop runs 17** (installed at different times, never reconciled). This matters the moment you copy data between them: a `pg_dump -F c` (custom/binary format) taken with `pg_dump` 18 **cannot** be restored with the 17.10 `pg_restore`/`psql` on the laptop — a version mismatch in that direction fails outright. Dump with `--format=plain` (plain SQL) instead when moving data *from* the server *to* a lower-versioned dev machine; a plain-text dump from the newer version loads fine into the older one as long as it doesn't use PG18-only DDL (it didn't, for this schema — no generated columns, no new syntax). Going the other way (17 → 18) isn't a problem either format. Also: the dev laptop's `zepol` role may not have `CREATEDB` (only the Windows installer's `postgres` superuser does) — restoring into a fresh database needs `ALTER ROLE zepol CREATEDB;` or a superuser to `CREATE DATABASE` first, and dropping the old database before confirming the new one can actually be created leaves you with neither until that's granted.
- **The server's real `zepol` Postgres role password is not `zepol`/`zepol`, the hardcoded default in `database.py`** — confirmed by direct `psql`/`pg_dump` connection attempts with that password failing "la autentificación password falló" from every angle tried (IPv4, IPv6, with/without SSL), while the actual running backend connects and serves real data fine, and `.env` genuinely does not exist on the server (see the `.env`/`SECRET_KEY` gotcha below) and no `DATABASE_URL` override exists at the user or machine environment-variable level either. Where the real credential actually comes from is unresolved — not urgent (a cold-started backend process does successfully connect, so a normal restart isn't at risk), but don't assume you can `psql` in with the default password on this server. **To dump/inspect the server DB without knowing that password**: don't try to extract or print it — write a small script that imports `app.database.DATABASE_URL` (the exact object the running app already resolves successfully) and pipes it straight into `pg_dump` as a connection URI via `subprocess`, entirely inside the script; run it over SSH from `sistema-mp/backend` with the venv's `python.exe`. This dumps the real DB using whatever credential actually works, without that credential ever appearing in a terminal, a command history, or this conversation. (The auto-mode classifier will actively block a bare attempt to print/`echo` the resolved `DATABASE_URL` in full — that block is correct; route around it by never printing it; use it, don't reveal it.) Clean up the script from the server afterward (it briefly lives inside the git-tracked `sistema-mp/backend/`, so a stray copy in a commit would be a real leak — delete it after each use, don't leave it lying around).

### Frontend (`sistema-mp/frontend`)

```
npm run dev      # electron-vite dev server + Electron window
npm run build    # typecheck-free production bundle (main+preload+renderer)
npm run dist     # build + electron-builder installer
npx tsc -b --noEmit   # typecheck only
```

- Uses Vite 7 pinned deliberately — `electron-vite` doesn't yet support Vite 8, and `@vitejs/plugin-react` is pinned to `^4` for the same reason. Don't bump either without checking `electron-vite` compatibility first.
- Only one dev instance should run at a time. `npm run dev` spawns Electron + a Vite dev server (port 5173, auto-increments if busy); killing the terminal doesn't always kill the child `electron.exe`/`node.exe` processes cleanly, and stale ones left running cause the next launch to silently fail to hot-reload or fail to fetch data. If a screen shows unexpectedly empty/stale data, check for leftover `electron.exe`/`node.exe` processes before assuming it's a backend/DB bug.
- **`ELECTRON_RUN_AS_NODE`**: if this env var is set in the shell (some tooling sets it), any `electron` binary launched from that shell runs as plain Node instead of a real Electron app and crashes on `electron.app.getPath`. Unset it for the dev command: `env -u ELECTRON_RUN_AS_NODE npm run dev`.

## Architecture

### Backend: Model / Controller / View split

`app/` is organized as MVC, but note the FastAPI-specific meaning of "View": there's no HTML/templates, `views/*.py` are just the route handlers (naming borrowed from Django's convention of calling a request handler a "view" even without one).

- `models.py` — SQLAlchemy ORM (single file, all tables).
- `schemas.py` — Pydantic request/response shapes (single file).
- `controllers/*_controller.py` — all business logic and validation. Route handlers never touch the DB or raise domain errors directly; that all lives here.
- `views/*_view.py` — thin: parse request → call controller → shape response with a `_serializar()` helper. Each view file owns its own serializer rather than sharing one, because each response shape pulls in different relationship data. **Gotcha this has already caused**: a `_serializar()` that builds its Pydantic model by listing fields explicitly (most of them, e.g. `materiales_view.py`) has to be updated by hand every time a field is added to that schema — `MaterialOut` in `catalogos_view.py` didn't need a matching edit when `usa_bobinas` was added because it's `ConfigDict(from_attributes=True)` and gets returned straight from the ORM object, but `materiales_view.py`'s hand-built `MaterialAdminOut(...)` did, and missing it 500'd every `GET /materiales` with a Pydantic "field required" error. When adding a field to a schema, grep for every `_serializar` that constructs that schema by name, not just the one you were already editing.
- `main.py` wires the view routers together.

The real presentation layer (what the user sees) is the separate Electron/React app, not anything in this backend.

### Core domain model: OT → OtProceso → OtMaterial → Entrega/Devolucion

This is the part that needs multiple files to understand, so it's worth internalizing before touching `ordenes_controller.py`, `entregas_controller.py`, `devoluciones_controller.py`, or `models.py`:

- An **`OrdenTrabajo`** (OT) has exactly one `cliente` **and** exactly one `diseño` — both live at the OT level, not per proceso. (This flip-flopped once: diseño briefly lived on `OtProceso` because a single OT *could* in theory carry different designs per process step, but the plant confirmed that in practice an OT is always one client + one design regardless of how many processes it goes through, so it moved back up. Don't split diseño back out to `OtProceso` without being asked again — check with the user first, this one has reversed direction before.)
- An OT goes through one or more **`OtProceso`** steps — (OT, proceso, máquina). A `Maquina` belongs to exactly one `Proceso`; the composite FK `(maquina_id, proceso_id) → maquinas(id, proceso_id)` makes an invalid combination (e.g. Confección with máquina F4) impossible at the DB level, not just in application code.
- Under one `OtProceso`, each material requested is its own **`OtMaterial`** ("pedido") with its own `cantidad_requerida`. One OT+proceso step commonly has several pedidos (e.g. OT 2121 in Laminación needs 500kg of PA15520 *and* 200kg of PA15V — two `OtMaterial` rows under the same `OtProceso`). Any active `Material` can be requested in any proceso — there used to be a `material_procesos` allow-list table restricting this, but it was **removed** after the plant confirmed the restriction was fictional (e.g. Extrusión genuinely accepts any raw material); don't reintroduce a proceso↔material gate without being asked.
- **`Crear OT` (`DetalleOt.tsx`, `POST /ordenes-trabajo/detalle` → `ordenes_controller.guardar_detalle`) never assigns proceso/máquina.** This reversed direction once already (see git history) — it used to have per-proceso blocks with a máquina `<Select>`, but the plant clarified that at OT-creation time nobody knows yet which máquina will run each material; that's a floor-scheduling decision made later. So today Crear OT only sets cliente/diseño/datos comerciales (see `CamposComercialesOt` below) and a **flat list of materiales** (`material_id` + `cantidad_requerida`, no proceso). Each material becomes a row in **`OtMaterialPendiente`** ("pendiente" — not yet a real pedido). Don't re-add a proceso/máquina picker to this screen without being asked again.
- **A pendiente can receive materia prima *before* it has a proceso** — `OtMaterial.insumo_de_pendiente_id` (FK to `ot_materiales_pendientes`, mirror of `insumo_de_id`). This exists because the two decisions happen at different times: the materia prima physically leaves almacén today so that the material can be manufactured, but which proceso/máquina will consume the *result* is often decided only when producción hands it back. Forcing the assignment at materia-prima time meant inventing the data — the plant hit this immediately and it read as a validation bug. So in `PendienteCard` proceso/máquina are **optional**, and only become required when the pendiente's own material is being delivered (`requiereAsignacion` = the pedido's own cantidad is filled in); `POST /entregas` then takes `pendiente_id` instead of `ot_material_id` (exactly one of the two; `pendiente_id` is rejected without `como_materia_prima`, since an unassigned material can't be delivered). `promover_pendiente` re-points those rows to the real pedido (`insumo_de_id` set, `insumo_de_pendiente_id` cleared) before deleting the pendiente row, and `OtMaterialPendienteOut.materias_primas` lists their códigos so the card can show what's already been loaded. Don't make proceso/máquina mandatory again on that card, and keep its copy generic — the plant pushed back on wording that framed "hay que fabricarlo" as the special case, since any material in any OT can need others to complete it.
  The counterpart is `PendienteIngresoCard` in `RegistrarDevolucion.tsx` ("Material que entrega producción"): a pendiente with materia prima never became a pedido, so it doesn't appear in `/consumo` and the ingreso a almacén had nowhere to go — that was a real dead end the plant hit. Those pendientes are listed **in the same selectable list as the pedidos** (not in a section of their own) and their card takes **only the quantity** — producción delivers in tandas (two bobinas today, one tomorrow), so the material has to stay in the list after the first ingreso instead of looking closed; each submit is one more `Devolucion` row and `OtMaterialPendienteOut.total_ingresado` shows the running total. `Devolucion` therefore hangs off *either* `ot_material_id` *or* `ot_material_pendiente_id` (DB `CHECK` enforces exactly one), and `promover_pendiente` re-points those rows too. **Never ask for proceso/máquina when registering an ingreso** — the plant's rule, and it's the right one: this movement is producción → almacén, and *almacén has no machines*. Proceso and máquina describe where material is consumed, so they belong to the opposite movement (almacén → producción, i.e. Registrar Entrega), which is where the pendiente finally gets promoted. A `pendiente_id` devolución is rejected unless `es_ingreso_produccion` is true: nothing was ever delivered from it, so it can't have sobrantes. Consumers that group devoluciones by pedido (`Historial.tsx`, `RegistroSid.tsx`) must skip rows whose `ot_material_id` is null.
- **A pedido's proceso/máquina can be corrected after the fact** — `ordenes_controller.mover_pedido` / `PATCH /ot-materiales/{id}/proceso` / the `MoverPedido` block inside `PedidoEntregaCard`. Same reason as above: the proceso is often chosen before it's certain, so getting it wrong can't mean redoing the OT or editing the DB by hand (that's exactly what happened to OTs 666/1111, whose LDPE-3 ended up stuck in Extrusión under an older design). Entregas/devoluciones hang off the pedido, not the OtProceso, so they move with it untouched; the pedido's materia prima is deliberately **not** moved (it has its own proceso — consumed where it's made, not where the result is used). It reuses `crear_o_reutilizar_ot_proceso`, deletes the old `OtProceso` if nothing else is left in it, and returns a clear 400 instead of a DB error when the destination already has a pedido for that same material (`UNIQUE (ot_proceso_id, material_id)`).
- **Proceso/máquina get assigned in `RegistrarEntrega.tsx`, at the moment of the first entrega**, via `POST /ot-materiales-pendientes/{id}/promover` (`ordenes_controller.promover_pendiente`). This is the only place `OtProceso`/`OtMaterial` get created (mirrors the old `guardar_detalle` idempotent-creation logic: reuses an existing `OtProceso` for that (ot, proceso, máquina) combo instead of duplicating). The frontend does "asignar proceso+máquina" and "`POST /entregas`" as two calls chained in one submit (`PendienteCard` in `RegistrarEntrega.tsx`), so from the user's point of view it's one action. A pendiente whose `codigo_mp` (from Excel — see below) doesn't match any `Material.codigo_mp` has `material_id = NULL` and the UI asks the user to pick the right catalog material via `Combobox` before it can be promoted.
- **`Entrega`/`Devolucion` never create OT structure implicitly** — `entregas_controller.registrar_entrega` is a thin `ot_material_id` lookup, nothing more. If `EntregaCreate` ever needs to grow proceso/máquina/material fields again, that's a sign something regressed back toward the old implicit-creation design; don't do that.
- **`RegistrarEntrega.tsx` registers against multiple pedidos in one submit** — added after the single-pedido version proved too slow for an OT with 3 pedidos. Pedido cards are multi-select (toggle, not radio); each selected pedido gets its own bobinas sub-form; submit loops `POST /entregas` once per selected pedido (no batch endpoint on the backend) and reports partial success/failure per material rather than failing the whole batch on one error. Pendientes (see above) render as separate cards above/alongside the normal pedido list, each with its own proceso/máquina pickers. Anything registered from a `PendienteCard` feeds the same green confirmation banner as the rest (`onRegistrado` hands the created `Entrega`s up) and clears the card's form, scrolling the banner into view — without that, saving from a card far down the page left no visible sign and invited a second click that would register everything twice.
- **`Entrega`** rows are partial or full deliveries against one `OtMaterial` — several entregas (different dates) commonly target the same pedido (e.g. 200kg today, 300kg tomorrow, summing toward the 500kg required).
- **`Devolucion`** rows also hang off `OtMaterial`, not off a specific `Entrega` — once material is on the floor it's no longer attributable to a specific delivery batch, so "cuánto se puede devolver" is computed against the *cumulative* entregado/devuelto totals for that pedido/material (see `pedidos_controller.total_entregado_pedido` / `total_devuelto_pedido` and the per-material variants below), not against a single entrega. **This is informational only, not a hard gate** — `devoluciones_controller.registrar_devolucion` used to reject a devolución that exceeded the computed disponible, but the plant asked for that to become a non-blocking warning (shown client-side in `RegistrarDevolucion.tsx`'s `PedidoDevolucionCard`) instead: the entregas bookkeeping can be incomplete or the physical count can differ from it, and an operator's real count should never be refused by the system's own arithmetic. Don't reintroduce a `raise HTTPException` there without being asked again.
- **Entregas and devoluciones can be corrected or deleted after they're saved** — `entregas_controller.editar_entrega`/`eliminar_entrega`, `devoluciones_controller.editar_devolucion`/`eliminar_devolucion` (`PATCH`/`DELETE /entregas/{id}`, same shape on `/devoluciones/{id}`). This is the one deliberate exception to the system's general rule that real movement locks a pedido (contrast `ordenes_controller._bloquear_si_pedido_tiene_movimientos`) — planta staff aren't always confident typing on a computer, and there was no way to fix a wrong cantidad/fecha/material once saved short of editing the DB by hand. Each row carries `editado_por_id`/`editado_en` (nullable), rendered inline on its own card in `Historial.tsx` ("Editado por X el fecha", `text-primary`) so the correction is visible right where the data lives. **Don't build a separate audit-log table for this** — one was tried (a dedicated `auditoria` table + a "Bitácora de correcciones" panel) and explicitly walked back for being more detail than anyone wanted to read; the two columns + inline note are the settled design. **Once `sid_completado` is true for that specific movement, editing/deleting it is blocked** (`_bloquear_si_entrega_tiene_sid`/`_bloquear_si_devolucion_tiene_sid`, 400) — the SID is an external trámite, so a movement already reported can't silently change under it; the fix path is un-checking it in Registro SID first, which is deliberately still always allowed.
- **An individual `Entrega` can be pinned to a different proceso/máquina than its pedido's** — `Entrega.ot_proceso_id` (nullable FK to `OtProceso`; `NULL` = same as `OtMaterial.ot_proceso_id`, the normal case, so this is fully backward-compatible with every entrega that predates the column). Exists for the same floor-reality reason as the material substitution below: a later partial delivery of the same pedido — especially alongside a material substitution — sometimes runs on a different máquina than an earlier one did, and that shouldn't force moving the *whole* pedido (`mover_pedido` moves every entrega/devolución of that pedido, past and future — see above, don't conflate the two). `EntregaCreate.proceso_id`/`maquina_id` do double duty depending on `como_materia_prima`: with it, unchanged — they're the new materia-prima pedido's home; without it, they're an optional override for *this one* entrega, resolved through the same `ordenes_controller.crear_o_reutilizar_ot_proceso` helper (made non-private for this — mover_pedido/promover_pendiente/materia-prima creation all still share it). `EntregaOut.proceso`/`maquina`/`proceso_id`/`maquina_id` report where *this entrega* actually landed (override or pedido's own), which is a different question from `Consumo.proceso`/`maquina`/`proceso_id`/`maquina_id` (the pedido's own, now also exposed by `vista_consumo` for exactly this comparison) — the frontend diffs the two to decide whether to show a highlight, don't assume they're always equal. `RegistrarEntrega.tsx`'s `EntregaDelPedido` offers the override behind a "¿Se entregó en otro proceso/máquina?" toggle (preselected to the pedido's own values, so the common case needs zero extra clicks); `EntregaUpdate` carries the same pair so it can be corrected later from `Historial.tsx` too.
- **The material(s) actually delivered can differ from the material pedido, and a pedido can need extra materials the OT never listed.** These are two different things and the UI keeps them visually and mechanically separate — conflating them was a real complaint from the plant:
  1. **Sustitución 1 a 1** (`EntregaDelPedido`, any pedido): almacén doesn't have the exact micronaje/ancho requested and hands out an alternativa (pedido asks BOPP20520, almacén gives BOPP20560) or a full cambio de estructura (PET20520 instead of a BOPP). One `Entrega` against the pedido on screen with a different `material_id`. The picker stays hidden behind a "¿Se entregó un material distinto?" link, since most of the time nothing needs to change.
  2. **Materia prima** (`MateriasPrimas` / `FilaMateriaPrima`, **any pedido of any proceso**): the pedido's material can't be handed over as-is because it has to be made from other materials first — the OT asks for LDPE-4 and almacén only has LDPE-1 and LDPE-2, which are mixed to produce it. Nothing is being substituted, so this does **not** touch the pedido's own `material_id`: each material becomes **its own `OtMaterial` in the OT** (see the next point). Behind a "+ Agregar materia prima" button, repeatable.
  Keep (2) available everywhere, not gated on proceso — the plant was explicit that "the OT asks for a code and we need another material to complete it" happens in any OT, and an earlier Extrusión-only version was rejected for that reason. Equally, **never filter which materials can be picked as materia prima** — any active catalog material qualifies (same principle as the removed `material_procesos` allow-list above).
  Mechanically: both `Entrega` and `Devolucion` carry their own `material_id`, separate from `OtMaterial.material_id` (the pedido) — `Entrega.material_id` defaults to the pedido's material when not given (the common, no-substitution/no-recipe case) but can be overridden; `Entrega.observacion` is an optional free-text note (deliberately optional, and there's deliberately **no** flag distinguishing "alternativa" from "cambio de estructura" from "insumo de receta" — the plant asked for all of these to be treated the same). Each `Entrega`/`Devolucion` row is still always a single material (never mixed within one row) — a multi-material delivery against one pedido is just several `Entrega` rows, one per material, which is why `RegistrarEntrega.tsx`'s `EntradasMaterial` component (shared by `PedidoEntregaCard` for existing pedidos and `PendienteCard` for a pendiente's first entrega) renders a **repeatable list** of {material, cantidad, nota} entries per pedido — "+ Agregar materia prima" appends another entry, and `enviarSeleccion` submits one `POST /entregas` per entry (the pedido's own delivery plus one per materia prima), with per-entry partial-failure reporting — there is no batch endpoint. `RegistrarDevolucion.tsx`'s `PedidoDevolucionCard` mirrors this for devoluciones, except the material picker there is a `Select` constrained to `pedidos_controller.materiales_entregados_pedido` / `GET /entregas/materiales-entregados/{ot_material_id}` (materials that were *actually* delivered against that pedido, each with its own total entregado/devuelto/disponible) rather than the free catalog — you can't return a material that was never delivered, so there's no reason to offer it. The exception is an **ingreso a almacén** (see below), which skips that query entirely and registers against the pedido's own material. `vista_consumo.material_sustituido` (a boolean, computed via `EXISTS` against `entregas`/`devoluciones` where `material_id <> ot_materiales.material_id`) tells the frontend when it's worth showing the real-material breakdown at all (`Historial.tsx`'s per-pedido badge, `RegistroSid.tsx`'s highlighted "hubo sustitución" box with bobina-level detail grouped by material) instead of querying it for every row. For the 1-to-1 substitution case, the pedido-level aggregate (`cantidad_requerida` vs `total_entregado`) intentionally stays material-agnostic — kg delivered of any substitute still counts toward fulfilling the pedido's requested quantity. **This does NOT extend to materia prima** — see the next point: it isn't a substitution at all, it gets pedidos of its own, so nothing of it lands on the parent pedido's `total_entregado`.
- **Materia prima: a material needed to complete another pedido becomes its own `OtMaterial`, with its own proceso and máquina.** `OtMaterial.insumo_de_id` (self-referencing FK, only set at creation — never overwritten when an existing pedido is reused) points at the pedido it completes. Worked example, OT 2222 asking for 200kg of LDPE-4 to be used in Impresión — F4:
  - The LDPE-4 pedido is assigned to **the proceso where the material is actually used** (Impresión — F4), not to Extrusión. This matters and reversed an earlier design: LDPE-4 used to get a pedido in Extrusión ("fabricarlo") *plus* a second one in the destination proceso ("usarlo"), and the plant rejected it outright — the pedidos list read as if the OT needed 400kg of LDPE-4, and it claimed the material "went through Extrusión" when Extrusión was only how it got made. **One material requested by the OT = one pedido. Don't reintroduce a second pedido for the same material.**
  - Almacén has no LDPE-4, so from that pedido (or from the pendiente, if it isn't assigned yet — see above) the operator adds LDPE-1 and LDPE-2 as materia prima (`EntregaCreate.como_materia_prima` + `material_id` + `proceso_id` + `maquina_id`). `ordenes_controller.crear_pedido_materia_prima` gives each one its own `OtMaterial` with `insumo_de_id` = the LDPE-4 pedido and `cantidad_requerida` = the quantity being delivered, and the entrega lands there. **Each picks its own proceso/máquina** (Extrusión — CHINA), which is deliberately *not* inherited from the parent: materia prima is consumed where the material is made, not where the result is used. Reuse is idempotent (`_crear_o_reutilizar_ot_material`): delivering more LDPE-2 later lands on the same pedido and does not bump its `cantidad_requerida`, so the extra shows as delivered above requested.
  - Because each `Entrega.material_id` equals its own pedido's material, **none of this is flagged as a substitution** (`vista_consumo.material_sustituido` stays false). That was the original complaint: nothing was replaced, new pedidos were born.
  - **The "+ Agregar materia prima" UI button (`RegistrarEntrega.tsx`) was removed (2026-09-15)** after real cases where it made things worse instead of better: the "padre" pedido a materia prima needs to attach to (`insumo_de_id`) sometimes was never loaded into the OT at all (the client's own OT creation is what's incomplete, not something sistema-mp can fix), or the would-be materia prima (e.g. PEMET-1) had itself already been registered as its own independent pedido, leaving nothing sane to attach it to. Every delivery that used to go through that button now goes through **`EntregaLibreForm`** ("Entregar un material que la OT no tiene", the `numero_ot` mode of `EntregaCreate`/`crear_pedido_libre`) instead — a loose pedido, no `insumo_de_id` link, but always creatable regardless of whether the OT lists the right parent. `EntregaCreate.como_materia_prima`, `ordenes_controller.crear_pedido_materia_prima`, and `OtMaterial.insumo_de_id`/`insumo_de_pendiente_id` are **not removed from the backend** — historical pedidos linked this way still exist and still render their "⚗ se fabrica en esta OT" / "materia prima de X" badges (`Historial.tsx`, `RegistroSid.tsx`, `RegistrarEntrega.tsx`'s pedido list, the `pendiente.materias_primas` info box in `PendienteCard`) exactly as before — there's just no UI path left that creates a *new* one. Don't resurrect the button without checking back with the plant on whether the underlying OT-creation gap (missing parent pedidos) has actually been fixed first.
- **A `Devolucion` covers two directions of "material coming back to almacén", separated by `Devolucion.es_ingreso_produccion`.** Both are producción → almacén, which is why they share the table and the Registrar Devolución screen, but they count differently:
  - `FALSE` — **sobrante**: material that had been delivered and wasn't used. Counts into `vista_consumo.total_devuelto` and subtracts from `consumo_neto`, as always.
  - `TRUE` — **ingreso a almacén**: the material *manufactured in this OT* entering stock for the first time (the 200kg of LDPE-4 that came out of mixing LDPE-1 and LDPE-2). It was never delivered, so subtracting it would give a nonsense neto — it goes to its own `vista_consumo.total_ingresado` and `consumo_neto` ignores it. `pedidos_controller.total_devuelto_pedido`/`total_devuelto_material` filter it out too.
  `RegistrarDevolucion.tsx` offers the choice ("¿Qué estás registrando?") only on pedidos with `tiene_materia_prima`, defaulting to `ingreso` — that's what an operator opening such a pedido almost always came to do — and renders that mode in ámbar with a "Registro de ingreso a almacén" banner, because the plant asked for it to be unmistakable at a glance. In `ingreso` mode there is no material picker (it's the pedido's own material) and no "disponible para devolver" warning: nothing was delivered to compare against. A pedido with materia prima can still receive real sobrantes later, which is why it's a choice and not an assumption.
- **The full cycle, and the order the screens enforce it:** Crear OT / Excel lists LDPE-4 → Registrar Entrega assigns it to Impresión — F4 and adds LDPE-1/LDPE-2 as materia prima in Extrusión — CHINA (their entregas are what actually leaves almacén) → Registrar Devolución records the 200kg of finished LDPE-4 as an **ingreso a almacén** → Registrar Entrega delivers those 200kg against the LDPE-4 pedido as an ordinary entrega, and only then does it reach COMPLETO. `consumo_controller._estado_entrega` has no special cases left: **every** pedido advances on `total_entregado`, including one whose material is manufactured in-house. An earlier version branched on `proceso == "Extrusión"` to compare against a different total — that's gone, don't bring it back.
- `vista_consumo` surfaces this as `es_materia_prima` (`insumo_de_id IS NOT NULL`), `insumo_de_codigo_mp` (the material it completes, via a LEFT JOIN back to `ot_materiales`/`materiales`), `tiene_materia_prima` (the reverse `EXISTS` — this pedido's material is made in this OT) and `total_ingresado`. The frontend reads these rather than re-deriving anything from proceso names: a "materia prima de LDPE-4" badge and a "se fabrica en esta OT" badge (⚗, `Beaker` icon) in `RegistrarEntrega.tsx`, `RegistrarDevolucion.tsx`, `Historial.tsx` and `RegistroSid.tsx`; an "Ingresó a almacén" tile in `Historial.tsx` shown only when `total_ingresado > 0`; and in `RegistroSid.tsx` the Devueltos tab lists pedidos with `total_devuelto + total_ingresado > 0`, since an ingreso is its own trámite just like a sobrante.
- `vista_consumo` (a SQL view) is the one-row-per-`OtMaterial` summary (cliente/proceso/diseño/máquina/material/required/entregado/devuelto/neto) that "Consulta", "Historial de OT", the devolución/entrega pedido-pickers, and "Registro SID" all read from; `consumo_controller` adds a computed `estado_entrega` (PENDIENTE/PARCIAL/COMPLETO) on top by comparing `cantidad_requerida` to the delivered total. See the DB gotcha above — this view has to be manually recreated on the live DB after edits.
- Composite FKs (`ot_procesos.(maquina_id,proceso_id)`, `ot_materiales.(ot_proceso_id,proceso_id)`) exist specifically to make the "máquina must belong to the chosen proceso" rule unbreakable at the database layer, not just validated in `controllers/`. When adding a new table that references one of these, prefer extending the composite-FK pattern over re-validating in Python alone.
- Bobina weight rows (`entrega_bobinas`, `devolucion_bobinas`) deliberately have **no unit column** — the unit always comes from `Material.unidad`. This was a specific fix for a real data-entry risk (operators mixing kg/units) in the original Excel workflow; don't add a per-row unit field back in.
- **The SID ("SID", a plant-side external trámite) is tracked per individual movement, and the pedido's status is a derived aggregate** — this reversed an earlier design where the pedido was marked directly, because the ingeniero files the SID day by day, so an entrega registered today can't inherit the "done" mark that yesterday's entrega earned. The real checkbox is `Entrega.sid_completado` / `Devolucion.sid_completado` (`POST /entregas/{id}/sid/completado|pendiente`, same shape on `/devoluciones/{id}` → `sid_controller.marcar_entrega_sid`/`marcar_devolucion_sid`). `OtMaterial.estado_sid_id` and `OtMaterial.sid_devolucion_completado` are then **recomputed** from those (`sid_controller.recalcular_estado_entrega`/`recalcular_sid_devolucion`: complete only when the pedido has at least one movement and *every* one of them is checked) — never assign either of them directly outside those two functions. A new entrega/devolución therefore reopens its pedido automatically, since it arrives unchecked; `registrar_entrega`, `editar_entrega`, `eliminar_entrega` and their devolución counterparts all call the recalculation before committing for exactly that reason.
  - Consequence worth knowing: **4 of the 6 `estados_sid` catalog values are now dead.** The aggregate only ever writes PENDIENTE or COMPLETADO, so REGISTRADO, CORREGIR, CORREGIDO and ANULADO have 0 rows and no code path can produce them. `GET /catalogos/estados-sid` still returns all 6 and `api.listarEstadosSid` still exists in `api.ts`, but no screen calls it. Don't read the catalog as a list of states the system can actually be in.
  - The entrega SID and the devolución SID are two **independent** trámites against the same pedido (a pedido can be "SID de entrega done, SID de devolución still pending" or vice versa), which is why the devolución side is a plain boolean rather than reusing the `estados_sid` catalog.
  - `_bloquear_si_entrega_tiene_sid`/`_bloquear_si_devolucion_tiene_sid` gate on **that one movement's** `sid_completado`, not on the pedido's aggregate — un-checking that single entrega in Registro SID is what unblocks correcting it.
  - `Entrega`/`Devolucion` both have an `hora` column (`Time`, `server_default=func.current_time()`) that existed in the DB from the start but was never exposed — `EntregaOut`/`DevolucionOut` and their hand-built `_serializar()`s didn't include it, so the frontend only ever showed the date. Now exposed and shown everywhere a movement's fecha appears (`Historial.tsx`, `RegistroSid.tsx`) as `fecha hora` via `lib/fechas.ts`'s `formatearFechaHora`/`formatearFechaHoraCompleta`. If you add a new field like this to `Entrega`/`Devolucion`, check both the schema **and** the view's `_serializar()` — same gotcha as `materiales_view.py` above.
- **An entire OT can be deleted** — `DELETE /ordenes-trabajo/{numero_ot}` (`ordenes_controller.eliminar_ot`), gated behind `crear_ot`, with an "Eliminar OT" button in `DetalleOt.tsx` shown once an existing OT is loaded. Rejected (400) if **any** entrega/devolución anywhere in the OT (including pendientes' ingresos) already has `sid_completado` — the SID is an external trámite, so an OT already reported can't just vanish. Deletes materia prima (`insumo_de_id IS NOT NULL`) before the pedidos they complete, to satisfy the self-referencing FK on `ot_materiales`. Doesn't touch the Excel row — that stays the client's.
- **Deleting a pedido's last movement reverts it to a pendiente, instead of leaving it "assigned" forever at 0kg** — `ordenes_controller.revertir_a_pendiente_si_vacio`, called from `entregas_controller.eliminar_entrega` and `devoluciones_controller.eliminar_devolucion` right after the delete. It's the mirror image of `promover_pendiente`: if the pedido has zero entregas and zero devoluciones left, it gets deleted and a fresh `OtMaterialPendiente` takes its place (same material/cantidad, no proceso/máquina); its own materia prima (if any) gets re-pointed via `insumo_de_pendiente_id`, same as `promover_pendiente` does in reverse; the `OtProceso` gets deleted too if nothing else is left in it. Doesn't apply to a materia-prima pedido itself (`insumo_de_id IS NOT NULL` — it was never a pendiente, there's nothing to revert to). Added after a real case (OT 77777) where deleting a wrong entrega left the pedido looking "already in progress" in both Crear OT and Registrar Entrega even though nothing had actually been delivered.
- **A pendiente's `codigo_mp` is never overwritten when it gets resolved to a catalog material** — `ordenes_controller.actualizar_pendiente` used to set `pendiente.codigo_mp = material.codigo_mp` once `material_id` was assigned, which silently discarded the original Excel text (e.g. "LDPE45840") the moment someone said "this is actually LDPE-3". `codigo_mp` now always stays the raw Excel string forever, and the UI resolves the display material separately via `material_id` — `PendienteIngresoCard`/its selection list in `RegistrarDevolucion.tsx` show the resolved catalog código as the main label with the original Excel código next to it (small, with the `FileSpreadsheet` icon) so it's traceable which Excel line this came from. This also fixed a second latent bug: `comparar_con_excel`'s `codigos_existentes` set used to go stale the moment `codigo_mp` got overwritten, since it no longer matched what a fresh read of Excel would report for that row.
  - The same "raw code vs. resolved code" split applies to **promoted** pedidos: `OtMaterial.codigo_mp_excel` (nullable, populated only by `promover_pendiente` from `pendiente.codigo_mp`) preserves the original Excel text after promotion, when it was set. `_codigos_materiales_en_sistema` (used by `comparar_con_excel`/`comparar_todas_con_excel` to find "materiales nuevos") checks **both** `material.codigo_mp` and `codigo_mp_excel` — without the second, a promoted pedido like "ZIPPER" (Excel) → "ZIPPER PP" (catálogo) shows up as a missing/new material forever, since the comparison never sees anything called "ZIPPER" in the system. Materia prima and pedidos created outside the pendiente flow (`crear_pedido_materia_prima`/`crear_pedido_libre`) leave `codigo_mp_excel` `NULL` — there's no Excel text to preserve for those.
  - **`actualizar_pendiente` allows resolving `material_id` for the first time even if the pendiente already has materia prima or an ingreso loaded** — this used to be blocked unconditionally by `_bloquear_si_pendiente_tiene_movimientos`, which made sense for changing cantidad or re-assigning an *already-resolved* material (that really could contradict what already moved), but not for the very first resolution: the materia prima loaded against a pendiente points at its **own** materials, so saying "this Excel code is actually catálogo material X" doesn't touch any of that. The guard now only fires on `cambia_cantidad` or `cambia_material_ya_resuelto`; the pencil-edit button in `DetalleOt.tsx`'s `FilaPendienteExistente` shows a material-only edit form (no cantidad field) in that in-between state instead of hiding entirely.
- **A material the OT never listed can still be entregado/ingresado, without editing the OT first** — added at the plant's explicit request after a real mis-resolution (OT 220289: a pendiente got resolved to the wrong catálogo material, which meant its materia prima was attached under the wrong identity) made clear that staff can't always wait for someone to fix the OT before registering what's physically moving.
  - **Registrar Entrega** → "Entregar un material que la OT no tiene": a third mode on `EntregaCreate`/`registrar_entrega` (`numero_ot`, alongside `ot_material_id` and `pendiente_id` — exactly one of the three) that calls `ordenes_controller.crear_pedido_libre` to create a **loose** pedido (no `insumo_de_id`, unlike `como_materia_prima`) with the given material/proceso/máquina, then delivers against it in the same request. Proceso and máquina are **required** here (unlike the normal mode) — the plant was explicit about this, since this is where the material is actually consumed.
  - **Registrar Devolución** → the button labeled **"Registrar ingreso de LDPE-3"** (renamed 2026-09-15 at Elias's explicit request from the more generic "Registrar ingreso de un material que la OT no tiene" — the component/behavior underneath is unchanged and still fully generic, this is a copy-only change; don't assume LDPE-3 is hardcoded anywhere in the logic, only in this one button's JSX text): `POST /ordenes-trabajo/{numero_ot}/pendientes` (`ordenes_controller.crear_pendiente_libre`, gated behind `registrar_devolucion`) creates a loose `OtMaterialPendiente` (material + cantidad only, **no proceso/máquina** — same "almacén has no machines" rule as everywhere else pendientes take ingresos), then `IngresoLibreForm` immediately registers the ingreso against it via the normal `pendiente_id` + `es_ingreso_produccion` path.
  - Both are idempotent on `(ot, material_id)` like the rest of the pedido/pendiente creation helpers — calling either twice for the same OT+material reuses the row instead of duplicating it.
- **`GET /ordenes-trabajo`'s row limit was raised from 200 to 2000** (`ordenes_controller.listar_ordenes`) after a real bulk-import day (238 OTs created within ~3.5 hours) silently pushed an older OT (220289) past the old cutoff — "Todas las OT" showed nothing wrong, it just never rendered that far down, and the day/month filter didn't help because the limit applies *after* the date filter. `ListadoOt.tsx` also groups results by day (most recent first, matching the query's `ORDER BY fecha_creacion DESC`) and sorts **within** each day by `numero_ot` descending — numeric-aware where possible (`compararNumeroOtDesc`) — instead of by insertion order, since a bulk-import day's insertion order has no relationship to the OT numbers involved.
- **`Comparar con Excel` also runs in bulk** — `GET /ordenes-trabajo/comparar-excel-todas` (`ordenes_controller.comparar_todas_con_excel`) reads the whole "oc mp" sheet **once** (`excel_oc_mp.leer_todas_oc_mp`, grouping every row by OT number with the same fusion logic as `leer_oc_mp` — see below) and diffs every OT already in the system against it in one pass, returning only the ones with real differences. Manual button ("Comparar todas las OT" in `ListadoOt.tsx`), same non-polling philosophy as "Buscar OT nuevas en el Excel" — reading a large file over SMB isn't free, so nothing calls this on a timer. ~5s over ~290 OTs / ~2000 Excel rows in practice. Tapping a result routes into `DetalleOt.tsx`'s existing single-OT compare/apply flow rather than duplicating that logic.
- **`Material.es_tinta`** flags the 3 pseudo-material codes that show up in the Excel "oc mp" MP-código slots but aren't physical raw material — `Laminación`, `FLaminación`, `Superficie` (confirmed by inspecting the real workbook: exact spelling/casing matters for the `codigo_mp` match). They're registrable in Crear OT (so the data isn't lost) but **excluded from `RegistrarEntrega.tsx`/`RegistrarDevolucion.tsx`'s pedido pickers** (client-side `.filter(p => !p.es_tinta)` on the `/consumo` and `/pendientes` results) since nothing is ever physically delivered/returned for them. Also excluded from "Registro SID"'s per-OT completeness math for the same reason — an ink-charge pedido would otherwise permanently block an OT from ever showing "Completado" there, since it can never get an entrega. Don't assume these 3 are the only ink-type materials in the catalog — there are many real `TL*`/`T*` ink codes in `materiales` that **are** physical deliverables and must stay `es_tinta = false`.
- **`Material.usa_bobinas`** decides whether `CampoCantidad` renders as several bobina rows with individual weights (the common case: kg of film/rollo) or as one plain quantity field — **this is a property of the material, chosen when it's created/edited, not inferred from `unidad`.** It used to be inferred (`esUnidadDiscreta`, a regex matching "unid" in the unit string, now deleted), which broke for ZIPPER (`unidad = "mts"` but genuinely not delivered in bobinas) — don't resurrect a unit-name heuristic for this. `CampoCantidad` takes an explicit `usaBobinas: boolean` prop; every call site resolves it from whichever `Material` is actually in play at that point (the chosen material in a `EntregaDelPedido`/`FilaMateriaPrima`/`PedidoDevolucionCard` entry, or the pedido's own material via `Consumo.usa_bobinas` / `BalanceMaterial.usa_bobinas` when nothing's been overridden) — never from the `unidad` string. `Materiales.tsx` and `CrearMaterialDialog.tsx` both expose a checkbox for it, plus `SelectorUnidad` (`components/SelectorUnidad.tsx`) for the unit itself — a `<Select>` of the unidades already used across the catalog (deliberately **not** a fixed enum: the catalog already has a dozen messy variants — `kg`/`Kg`/`KG`, `Unid.`/`unidad`/`unid`, `rollo`, `lts`, `cm2`... — normalizing them wasn't asked for) plus a "+ Otra unidad..." option that reveals a free-text field. When adding a brand-new material, `usa_bobinas` has no sensible default derivable from anything else — the person creating it has to say so explicitly.

### Excel OC-MP integration

The client keeps registering OTs in `OC 2025 bas.xlsx` (sheet "oc mp") in parallel with `sistema-mp`, indefinitely — this isn't a migration path to phase out, it's a permanent dual-system requirement. Built in phases (see `app/services/excel_oc_mp.py` for the column mapping — 36 columns, `COL_*` constants document exactly which Excel column is which):

1. **Read fallback (done).** `ordenes_controller.buscar_con_fallback` → `GET /ordenes-trabajo/{numero_ot}/buscar`: looks in the DB first, and if not found, opens the Excel (`msoffcrypto` to decrypt in-memory if a password is set, `openpyxl` read-only to parse — never touches disk, never saves) and returns that row tagged `origen: "excel"`. `DetalleOt.tsx`'s "Cargar OT existente" uses this and shows a read-only banner with all ~20 commercial fields + up to 6 materiales when the OT is Excel-only.
2. **Configurable file path (done).** `configuracion` table (generic key/value) holds `ruta_excel_oc_mp` and, separately, `excel_oc_mp_password` (empty/absent is valid — see the note about the client removing the password above), editable from `ConfiguracionExcel.tsx` (`GET/PUT /configuracion/excel-oc-mp`) — because the file's *name* never changes but its *location* can move by accident, and only the machine running the backend can meaningfully browse for it (the "Localizar archivo" button uses Electron's native dialog via a new `dialog:elegirArchivoExcel` IPC channel, so it only works run from the server PC). The PUT validates the path opens and has the "oc mp" sheet before saving.
3. **Save-to-DB (done).** `POST /ordenes-trabajo/{numero_ot}/importar-excel` (`ordenes_controller.guardar_desde_excel`) creates the `OrdenTrabajo` with all commercial fields, and each of its up-to-6 materiales becomes an `OtMaterialPendiente` (see domain model above) — matched against `materiales.codigo_mp` via case-insensitive `ilike`, left `material_id = NULL` if nothing matches (surfaced to the user to resolve manually rather than silently dropped).
4. **Write-back to Excel (done).** `excel_oc_mp.escribir_oc_mp` appends a new row to "oc mp" for any OT created natively in sistema-mp (never called for an OT that originated from Excel — `guardar_desde_excel` doesn't go through it). Reads use `openpyxl` because they're frequent and read-only-safe, but writes drive the *real* Excel application via COM (`pywin32`/`win32com`) instead of resaving the file with `openpyxl`, specifically because this workbook has other sheets (`oc resumen`, `indicador_tiempo`) with formulas reading "oc mp", and a blind resave risked silently breaking them. `pythoncom.CoInitialize()` is called explicitly per-call because COM initializes per-thread, not per-process, and FastAPI serves each request on a thread-pool thread. Runs with `Calculation` set to manual and every COM call wrapped in a retry helper (`_con_reintentos`), because a freshly-opened 6MB workbook with cross-sheet formulas stays "busy" (recalculating/indexing) for a while and rejects COM calls with `RPC_E_SERVERCALL_RETRYLATER` during that window — that's not the same as the file being locked by someone else. `OrdenTrabajo.sincronizado_excel`/`excel_sync_error` record the outcome; a failure (file locked/in use elsewhere, more than 6 materiales, etc.) never blocks saving the OT to the DB — `ordenes_controller._sincronizar_excel` swallows the exception — and can be retried manually via `POST /ordenes-trabajo/{numero_ot}/reintentar-excel`. **This write-back can only run on whichever machine hosts the FastAPI backend**, since COM automation drives the local Excel installation — it is not something a station PC can trigger remotely. A forceful kill of the backend process while a COM `Save()` is in flight (see the `--reload` gotcha above) can leave the workbook truncated/corrupt — the write itself has no protection against that, so avoid `taskkill /F`-ing the backend mid-write if at all avoidable.
5. **Discover new OTs (done).** `GET /ordenes-trabajo/nuevas-en-excel` (`ordenes_controller.listar_ots_nuevas_en_excel` / `excel_oc_mp.listar_ots_excel`) scans every row of "oc mp" and returns the `numero_ot`/cliente/descripción of the ones not yet in `ordenes_trabajo` — before this, the only way to pull an OT from Excel was already knowing its number (phase 1/3). `ListadoOt.tsx`'s "Buscar OT nuevas en el Excel" button is manual, not polled (opening/parsing the file isn't free); clicking a result opens `DetalleExcelDialog` (reuses `buscarOtConFallback` for the full preview) with Aceptar/Cancelar before calling the same `importarOtDesdeExcel` as phase 3 — review before import, same principle as `comparar-excel`/`aplicar-excel`.
6. **Bulk compare (done).** `GET /ordenes-trabajo/comparar-excel-todas` (`ordenes_controller.comparar_todas_con_excel`) — see the domain-model bullet above. Reuses `leer_todas_oc_mp`/`_procesar_fila_oc_mp`, the same one-pass-over-the-sheet machinery `leer_oc_mp` uses per-OT, just keyed by every OT number at once instead of searching for one.

**Gotcha that has already caused a real bug (fixed)**: `leer_oc_mp` used to `return` on the **first** row matching `numero_ot` and stop scanning. Two real cases break that assumption, both now handled by `_procesar_fila_oc_mp` accumulating across every matching row instead of stopping at the first:
- **More than 6 materiales.** `escribir_oc_mp` refuses to write more than 6 (`COLS_MATERIALES` only has 6 slots) and raises instead of splitting across rows — but the client, editing "oc mp" by hand, isn't bound by that: they just add a second row with the same `numero_ot` for materials 7+. Before the fix, `leer_oc_mp`/`comparar_con_excel` never saw that second row at all, so a material sitting only in it was invisible both at import time and when comparing — `comparar_con_excel` would happily report "sin cambios" on an OT that was visibly missing a material in the Excel file (real case: OT 220273, `BOPPMATE20520` on the overflow row).
- **The same `numero_ot` used for two distinct products.** Not an overflow case — the client sometimes registers two line items (different `descripcion_producto`/`codigo_producto`, e.g. "Trigo" vs. "Lenteja" bobinas) for the same client/vendedor/fecha under one shared OT number, each on its own row (real case: OT 220268, rows 2168/2169; also 220267, 220196). The "plata" fields (`total_ot`, `pu_usd`, `pt_usd`, `precio_total_pedido_usd`, etc.) are identical on both rows — confirmed by inspecting the real file — since they're the total for the *whole* OT repeated, not per product; summing them would double-count, so `_procesar_fila_oc_mp` takes those from the **first** matching row only and never touches them again. `descripcion_producto`/`codigo_producto` genuinely differ per row, so those two (and only those two) get **concatenated** with `" / "` across every matching row instead of keeping just the first — otherwise the second product silently disappears from the system's view of the OT even though nothing is technically wrong with the data. Materiales from every matching row are simply summed into one list either way (a row from the overflow case and a row from the two-products case look identical from `leer_oc_mp`'s perspective — both are "another row, same OT number").

`CamposComercialesOt` (`schemas.py`) is the shared Pydantic base for the ~20 commercial columns (fecha_seguimiento_mp, alm, so, tipo_trabajo, indicador, status_entrega_mp, vendedor, ciudad, fecha_pedido, fecha_entrega, descripcion_producto, codigo_producto, total_ot, entrega_mes, medida, equivalencia_kg, pu_usd, pt_usd, factura_clises, precio_clise_usd, precio_total_pedido_usd) — inherited by `OtDetalleCreate`, `OtDetalleOut`, and `OtExcelOut` so the same field set round-trips between Excel, the API, and the DB without repetition. `DetalleOt.tsx` has all of these as a collapsible "Datos comerciales / OC" section (default collapsed — most day-to-day use doesn't touch them).

**`OrdenTrabajo.uso_interno` (added 2026-09-15) opts an OT out of the Excel write-back entirely.** Rarely, the plant fabricates a material for its own internal use with no real client order behind it — staff said they'd number these arbitrarily (e.g. "001"). Writing a row to "oc mp" for one of these would misrepresent it as a real client pedido to anyone else reading that sheet, so `_sincronizar_excel` checks `ot.uso_interno` **first** and returns immediately if true — `escribir_oc_mp` is never even attempted (not "attempted and failed", genuinely skipped), and `sincronizado_excel` stays at its default `TRUE` since there's nothing to fail. Surfaced in `DetalleOt.tsx` as a **switch labeled "Registrar en Excel"** next to the "Datos de la OT" card title — green/ON (`bg-success`) is the default and normal case, red/OFF (`bg-destructive`) means `uso_interno`; deliberately no explanatory copy next to it, per Elias's request, and it locks (`disabled`) once the OT already exists (loaded from DB, from Excel, or just saved this session) since flipping it after the fact would silently change whether an already-decided OT starts/stops syncing. `OtDetalleCreate.uso_interno` only has an effect on the `guardar_detalle` branch that **creates** a new `OrdenTrabajo` — sent on an update to an existing OT, it's ignored. `OrdenTrabajoOut`/`OtDetalleOut` both expose it read-only so `ListadoOt.tsx` ("Uso interno" badge, replacing the "Excel pendiente" badge on that card since there's nothing pending to sync) and `DetalleOt.tsx` can show it after the fact.

**Never edit `OC 2025 bas.xlsx` (or the other two reference workbooks) directly, and never point dev/test work at the real file** — when inspecting it, decrypt to a scratch copy first.

**Gotcha that has already caused a real bug**: `excel_oc_mp._abrir_hoja` constructs `msoffcrypto.OfficeFile(f)` to sniff the file format, which silently advances `f`'s read position while peeking at the header — `is_encrypted()` doesn't rewind it afterward. On the *encrypted* branch this doesn't matter (`decrypt()` reads from the start on its own), but the *unencrypted* branch used to do `buffer.write(f.read())` right after, which returned only the tail of the file from wherever the peek stopped — a silently truncated, unparseable copy. `openpyxl.load_workbook` then failed with a cryptic zip error ("negative seek value"), caught and logged, and every caller (`leer_oc_mp`, `listar_ots_excel`) treated that identically to "genuinely not found" / "genuinely nothing new" — a real decrypted scratch copy got misdiagnosed as corrupted this way before the actual cause (missing `f.seek(0)` before the read) was found. This was dormant for a long time because the real workbook was always password-protected until the client removed it (see above) — that's exactly when it started being reachable in practice. The lesson generalizes: any read on `f` after constructing `OfficeFile(f)` or calling `.is_encrypted()` needs an explicit rewind first.

**Gotcha that has already caused real data loss in production**: the row-picking logic for a new OT's write-back used to be `_primera_fila_vacia` — "the first row (from `FILA_DATOS_INICIO`) whose OT-number cell is empty". That is **not** the same as "the first free row at the end". In a sheet edited by hand by the whole area, it only takes one row somewhere in the middle losing its OT number (deleted by accident, a row insertion, a sort/filter) for that row to look "free" while every other column still holds a real, loaded OT — and `escribir_oc_mp` only writes fields that have a value, so the orphaned row didn't get cleanly replaced, it got **merged**: some cells from the old OT, some from the new one, which is why the symptom read as two OTs "solapadas" rather than a straightforward overwrite. This happened for real (OT 220289 overwritten by OT 0001, 2026-09-08) and was reproduced on a scratch copy by blanking just the OT-number cell of an otherwise-full row and saving a new OT — it landed exactly on that row. Fixed (`07a41c2`) with two changes: `_primera_fila_libre` now finds the *last* row with real data (scanning every column, not just the OT one, so a damaged row doesn't look free either) and returns the row after it; and `_fila_ocupada` re-checks that exact destination row immediately before writing as a second, deliberately redundant guard — if it's not actually empty, `escribir_oc_mp` raises `ExcelEscrituraError` instead of silently merging into it. Both ignore `COLS_CALCULADAS` (columns 17/`COL_TOTAL` and 36/`COL_PRECIO_TOTAL_PEDIDO_USD`) on purpose — those two are formulas (`=F+H+J+L+N+P`, `=AI+AG`) precopied hundreds of rows past the last real data, so checking them would make every trailing row look "occupied" and writing would never find a destination. If you ever touch this logic again, keep both the "scan whole row, not just OT column" behavior and the pre-write re-check — either one alone would have missed the 220289 case (a damaged row with data in other columns, OT cell blank).

### OT sin número (S/OT), Fuelle y sincronización de borrados con el Excel (2026-09-17/19)

- **`numero_ot` se guarda y se busca siempre en MAYÚSCULAS** (`ordenes_controller._normalizar_numero_ot`; `consumo_controller`, `listar_entregas_por_ot` y `listar_devoluciones_por_ot` normalizan igual). Postgres compara texto sensible a mayúsculas: "sm-1" no encontraba "SM-1" en Registrar Entrega. Un número real de cliente es numérico, así que no le cambia nada.
- **S/OT** = OT sin número asignado por el cliente. Códigos `SM-#` (muestra) / `SO-#` (otros) — **sin barra ni espacio a propósito** (`numero_ot` viaja como segmento de URL: una "/" rompe las rutas `/ordenes-trabajo/{numero_ot}/...`; y al no ser puramente numérico Excel lo guarda como texto). La sugerencia sale de un contador persistido en `configuracion` (`contador_sot_muestra`/`contador_sot_otros`, `GET /ordenes-trabajo/siguiente-sot`), **no** de MAX+1: el contador solo avanza cuando la OT se crea con EXACTAMENTE el número sugerido (`_avanzar_contador_sot_si_corresponde`, detecta el tipo por el prefijo del propio `numero_ot`, no por un flag del frontend) — si alguien pone SM-10 a mano cuando iba en 5, sigue sugiriendo 5. Es distinto de `uso_interno`: las S/OT SÍ se escriben en el Excel. Switch "S/OT" en `DetalleOt.tsx`.
- **Trampa que confundió varias veces**: una fila de prueba que queda en el Excel se vuelve a importar sola por el vigilante aunque borres la OT de la base (`eliminar_ot` no toca el Excel), y al crear "la misma" OT el sistema ya la encuentra y la *amplía* en vez de crearla → el contador nunca avanza. Al limpiar pruebas hay que borrar también la fila del Excel (`eliminar_ot(borrar_excel=True)`).
- **Fuelle**: OT independiente numerada `F-<OT padre>` (ej. F-6321), con sus propios materiales/entregas/SID y fila propia en el Excel. Sin cambios de backend: es solo texto libre en `numero_ot`. `DetalleOt.tsx` (switch "Fuelle", excluyente con S/OT) busca la OT padre y copia cliente/diseño (del Excel solo cliente: "diseño" no es una columna de "oc mp").
- **"Comparar con Excel" ahora detecta lo que el Excel YA NO tiene** (`materiales_eliminados`, antes solo miraba Excel→sistema y decía "sin diferencias"). `aplicar_cambios_excel` (botón manual Y vigilante automático) borra esos pendientes/pedidos **salvo los "bloqueados"** (con entregas, devoluciones, materia prima o ingresos), que se dejan y se avisan.
- **OT que desaparece entera del Excel** (`_procesar_ots_ausentes_del_excel`, dentro de `sincronizar_automaticamente_excel`): solo considera OT con `sincronizado_excel=True` y no `uso_interno` (`False` significa "todavía no se escribió", no "se borró"); si `_ot_sin_movimientos_reales` se borra sola, si tiene movimientos solo se avisa (`RegistroExcelAutomatico.tipo='eliminada'`). **Freno**: más de `LIMITE_OTS_AUSENTES_AUTOMATICO` (3) ausentes de golpe → no borra ninguna (huele a lectura fallida del Excel, no a borrado real; en dev aparecieron 40 de golpe por un Excel de prueba reemplazado). Si el Excel no se puede leer, `leer_todas_oc_mp` lanza y la sincronización aborta antes de llegar acá.
- **Eliminar OT desde Crear OT** pregunta si también borrar su fila del Excel (`DELETE /ordenes-trabajo/{n}?borrar_excel=true`, `excel_oc_mp.borrar_fila_oc_mp`: vacía las celdas, no desplaza filas ni toca las 2 columnas de fórmulas). Devuelve 200 con `{excel_eliminado, excel_error}` (antes 204). Un fallo del Excel nunca revierte el borrado en la base. El error de SID al eliminar ahora dice qué material y qué fecha desmarcar (Registro SID no tiene vista "todo el historial" por fecha... salvo el modo **Todos** agregado).
- **`window.confirm()`/`alert()` nativos están prohibidos**: en Electron/Windows dejan la ventana sin recibir clics hasta hacer clic en la barra de tareas. Usar `useConfirm()`/`useAlert()` (`components/ConfirmProvider.tsx`, Radix Dialog).
- **`ExcelSyncToasts`** (montado en `Layout`): avisos flotantes de lo que hizo el vigilante en cualquier pantalla; sondea el mismo endpoint que `ConfiguracionExcel`.
- **Registro SID**: modo de fecha "Todos" (además de Día/Mes) y arreglo de un `useMemo` con dependencia equivocada (`devolucionesPorPedido`) que dejaba la tarjeta "SID de devolución" congelada en "Sin movimientos" al cambiar el filtro de fecha.
- **Dev/pruebas**: en la laptop, `escribir_oc_mp`/`borrar_fila_oc_mp` por COM fallan seguido con "llamada rechazada por el destinatario" tras muchas corridas seguidas y dejan `EXCEL.EXE` huérfano (`taskkill //F //IM EXCEL.EXE`); reintentar suele andar. Además, la PRIMERA llamada HTTP tras reiniciar `uvicorn --reload` se vio fallar dos veces (contador S/OT y un DELETE) y andar bien al repetir — no reproducido a pedido. `--reload` deja pares de procesos python duplicados: matar todos con `taskkill /T /F` antes de reiniciar.
- **Servidor**: `ruta_excel_oc_mp` está configurada como unidad mapeada `Z:\...`, que NO existe en una sesión SSH (solo en la interactiva) — no se puede leer/probar el Excel real desde `ssh zepol`. CLAUDE.md ya recomendaba UNC; sigue pendiente.

### Sugerencia S/OT, ingreso libre sin duplicar, y Descripción unificada (2026-09-19/22)

- **La sugerencia de S/OT saltea números ya usados**, no solo lee el contador a secas (`_primer_numero_libre_sot`, `sugerir_numero_ot_sin_asignar`) — una OT `SO-2`/`SM-3` creada directo en el Excel (o a mano, sin pasar por Crear OT) entra por el vigilante o por `guardar_detalle` sin tocar el contador, así que este se quedaba atrás y la sugerencia repetía un número ya existente. `_avanzar_contador_sot_si_corresponde` ahora compara contra ese mismo "primer libre desde el contador" (con `ignorar_numero_ot` para no contarse a sí misma), no contra el contador crudo.
- **"Registrar ingreso" (Registrar Devolución) nunca duplica un pedido que la OT ya tiene, sea como sea que lo tenga** — `ordenes_controller.resolver_ingreso_libre` (`POST /ordenes-trabajo/{numero_ot}/ingreso-libre`), llamado por `IngresoLibreForm`. Antes eso llamaba directo a `crear_pendiente_libre`, que solo revisa `OtMaterialPendiente` — si el material YA era un pedido real (`OtMaterial`, ej. materia prima ya entregada a Extrusión) no lo encontraba y creaba un pendiente aparte, que promovido aparecía como un material DUPLICADO en Registrar Entrega (caso real: LDPE-3 entregado a Extrusión + "Registrar ingreso de LDPE-3" después). `resolver_ingreso_libre` revisa primero `ot.procesos[].materiales` por `material_id`; si ya existe, la devolución se registra con `ot_material_id` contra ESE pedido (nunca `pendiente_id`); solo si no existe ni como pedido ni como pendiente, cae a `crear_pendiente_libre`. **(2026-09-22, revertido)** `IngresoLibreForm` tenía además un Select "¿Corresponde a un material que ya pide la OT?" para enganchar el ingreso a un pendiente del Excel sin resolver (ej. Excel pide LDPE40670 y es LDPE-3) — Elias pidió sacarlo: "Registrar ingreso" tiene que ser solo material + cantidad, sin preguntar nada más; ver la sección siguiente.
- **La "Descripción" de Crear OT (al lado de Cliente) ahora es `descripcion_producto`** (la columna real de "oc mp"), no `diseno` — el campo de afuera escribía `diseno`, que no es una columna del Excel, y la `descripcion_producto` real vivía escondida dentro de "Datos comerciales/OC" sin que nadie la completara. Al guardar, `diseno` se sigue llenando con el mismo texto (de respaldo, para no dejar en blanco las pantallas que muestran `diseno`) pero ya no es el campo editable. Fuelle copia esta descripción de la OT padre (del Excel, solo cliente — ver arriba).
- **Registro SID separa "SID de ingreso" de "SID de devolución"** — antes un ingreso a almacén (`Devolucion.es_ingreso_produccion`) se mezclaba dentro de la sección de devolución con la etiqueta "Ingreso a almacén", o solo se veía en la pestaña Ingresados si no tenía pedido. Ahora tiene su propia sección (entre entrega y devolución; 3 columnas en pantallas anchas, apiladas en angostas para no apretar nada) y los ingresos sin pedido de una OT también aparecen en la pestaña Todos, no solo en Ingresados.

### Frontend structure

- `src/main/` — Electron main process. Owns a small JSON config file (`app.getPath('userData')/config.json`, IPC channel `config:get`/`config:set`) storing `apiBaseUrl` — this is how each station PC points at the LAN server IP; there is no build-time env var for it.
- `src/preload/` — contextBridge exposing `window.api.{getConfig,setConfig}` to the renderer.
- `src/renderer/src/lib/` — `ConfigContext` (apiBaseUrl), `AuthContext` (JWT + usuario, persisted to `localStorage`, so a station stays logged in across restarts), `api.ts` (plain fetch wrapper; every function takes `baseUrl`/`token` explicitly rather than reading context internally, so it stays framework-agnostic and easy to call from TanStack Query hooks).
- `src/renderer/src/components/ui/` — hand-built shadcn-style primitives (not the shadcn CLI/package) — Button, Input, Label, Card, Select, Dialog (Radix `react-dialog`, used for confirmation/preview flows like `DetalleExcelDialog` in `ListadoOt.tsx`). Follow this pattern (Radix primitive + `cva` + `cn()`) rather than pulling in a component library. Two non-Radix additions: `combobox.tsx` — a searchable dropdown for picking a `Material` by código (needed once the catalog hit 564+ materials, a plain `<Select>` doesn't scale); shows the full list when the query is empty and filters as you type — don't let it go back to showing nothing on an empty query, that was a real regression once. `celda-copiable.tsx` — text plus a small per-field clipboard-copy button, used in `RegistroSid.tsx` so each cell copies independently instead of needing a "copy all" action.
- **Dates: `lib/fechas.ts`, and never `Date.toISOString()`.** The plant runs in `America/La_Paz` (UTC−4, no DST) and Postgres is configured to match, so `now()`/`current_time` write local time. `toISOString()` converts to UTC, which means between 20:00 and 23:59 local it yields **tomorrow's date** — this was a real, silent bug in all four copies of a duplicated `hoyISO()` at once: it was the default value of the `fecha` field in `RegistrarEntrega`/`RegistrarDevolucion` (so an entrega registered at night was saved one day ahead, and that wrong date then fed the Registro SID filter and Historial) and the default of the día filter in `ListadoOt`/`RegistroSid` (which therefore opened **empty** after 20:00, with nothing on screen to explain why). `hoyISO`/`mesActualISO`/`ultimoDiaDelMes` now live in `src/renderer/src/lib/fechas.ts` and build the string from local components (`getFullYear`/`getMonth`/`getDate`); import them instead of writing a fifth copy. The same rule applies on the backend: use `datetime.now()`, not `datetime.utcnow()`, so hand-set timestamps (`editado_en`) agree with the `func.now()` server defaults next to them.
- **Secondary actions are real `Button`s, never text styled as a link** (`text-primary hover:underline` on a bare `<button>`/`<a>`) — an explicit user preference, applies everywhere (e.g. RegistrarEntrega/RegistrarDevolucion's "¿Se entregó un material distinto?", "+ Agregar materia prima", "Ve a Crear OT"). A destructive/undo action (removing a materia prima row, canceling a material override) is an icon-only `X` button with a visible red frame (`rounded-md border border-destructive/40 text-destructive hover:bg-destructive/10`), not just red text on hover — it has to read as a button at a glance, not as decoration.
- Routing is `HashRouter` (not `BrowserRouter`) — required because the production build is loaded via `file://`, which doesn't support path-based routing.
- Catalog queries (procesos/máquinas/materiales) must surface `isError` state in the UI rather than failing silently — an empty dropdown with no error message is a real support problem on the plant floor (this bit already once — always show a retry banner, don't just let the `<Select>` render empty).
- **No wide tables for lists that can grow** — explicit user requirement ("no quiero que sea como en Excel, con scroll horizontal"). `Historial.tsx` and `RegistroSid.tsx` use card lists instead of tables for anything that can span the whole system's history; prefer that pattern over adding columns to `Consulta.tsx`'s table (single-OT results, inherently bounded, already pushes the limit at 9 columns) — a table is only acceptable when row count is bounded to one OT's pedidos, never for something that grows across all OTs.
- **Sidebar nav is hierarchical**, not flat (`components/Layout.tsx`, `NAV_ITEMS`/`NavGroup`) — a top-level item can carry a `children` array rendered as an indented, collapsible sub-list, so the sidebar stays short as more screens get added. Also **collapsible as a whole**: a hamburger button in the sidebar header hides it entirely (width animates to 0), and a floating hamburger button appears top-left to bring it back — `Card` had to become `forwardRef` for this (also reused for scroll-into-view on the Materiales edit form), don't remove that. Nav order currently: Crear OT (child: Todas las OT), Registrar Entrega (child: Historial de OT), Registrar Devolución, Consultar OT, Registro SID, Materiales, Máquinas, Excel OC-MP, Usuarios (admin-only — see access control below). Nested route paths (e.g. `entrega/historial` in `App.tsx`) are flat sibling routes to React Router, not actual `<Outlet>` nesting — the URL hierarchy is just for readability/grouping, and doesn't have to match the nav hierarchy 1:1.
- **OT workflow is a 4-screen pipeline**, plus `ListadoOt.tsx` / "Todas las OT" (child of Crear OT in the nav) as a cross-OT browse/search entry point — live search by OT/cliente/diseño, a día-vs-mes date filter (defaults to "today" so it doesn't dump the full history on open), a shortcut into Crear OT from each card, and a "Buscar OT nuevas en el Excel" button (manual, see Excel OC-MP phase 5) that opens a preview dialog (Aceptar/Cancelar) before importing, and a "Comparar todas las OT" button (manual, phase 6) that lists which already-imported OTs have drifted from their Excel row: `DetalleOt.tsx` / "Crear OT" (cliente+diseño+datos comerciales+flat materiales list, **no proceso/máquina** — see domain model above; also where an Excel-only OT gets imported into the DB) → `RegistrarEntrega.tsx` (search an OT, see both its existing pedidos from `GET /consumo?numero_ot=` *and* its `OtMaterialPendiente`s; entregas against pedidos are multi-select/batched, each pendiente gets promoted — proceso+máquina chosen — and delivered in one submit; `EntregaLibreForm` at the top covers a material the OT never listed at all — see the domain-model bullet on `crear_pedido_libre`) / `RegistrarDevolucion.tsx` (pedidos are multi-select/batched too, same pattern as entregas — toggle cards, one bobinas sub-form per selected pedido, submit loops `POST /devoluciones` once per pedido and reports partial success/failure; this is also where material fabricated in the OT enters almacén — see `es_ingreso_produccion` above; `IngresoLibreForm` is its `EntregaLibreForm` counterpart, for a material the OT never listed; pendientes don't apply here since a pedido has to exist first; a cross-OT "Materiales pendientes de devolver" list, same idea as "Todas las OT"'s recent-OTs list but at material granularity, shows what's outstanding before searching a specific OT) → `Historial.tsx` (browse any OT, full entrega/devolución history, unfiltered — shows tinta pedidos too, this one's meant to be the complete record; also where an individual entrega/devolución gets corrected or deleted — see the domain-model bullet above) → `RegistroSid.tsx` / "Registro SID" (cross-OT worklist for clearing the external SID backlog — see below). If `RegistrarEntrega` finds zero pedidos *and* zero pendientes for a typed-in OT, it links to `/crear-ot`. The discrete-vs-bobinas quantity sub-form (`CampoCantidad`, `components/CampoCantidad.tsx`) is shared between both screens — don't fork a second copy, extend the shared one. When a pedido has an entrega that substituted the material, pickers/lists show the material actually delivered, not the pedido's own código — showing the pedido's código there was a real bug (RegistrarDevolucion): it made the "disponible para devolver" numbers look like they belonged to the wrong material.
- **`RegistroSid.tsx`** has **four tabs**: Entregados, Devueltos, **Ingresados** (added 2026-09-15, see below), and Todos (default tab). A separate Pendientes/Completados/Todos filter (default Pendientes) narrows within whichever tab is selected. Entregados/Devueltos/Todos are all pedido-based (`Consumo`, one `estado_sid` for entrega, one `sid_devolucion_completado` for devolución — see domain model above), each grouped **one `Card` per OT** containing all of that OT's qualifying pedidos as checkbox rows inside — never render the OT number as its own card per pedido, that reads as multiple separate OTs (this was a real bug). Only pedidos with `total_entregado > 0` (Entregados) / `total_devuelto + total_ingresado > 0` (Devueltos) show up at all — an OT whose pedido hasn't been delivered yet doesn't appear there until it has. In the **Todos** tab, each material's card shows both trámites side by side (`SeccionSid` "SID de entrega" / "SID de devolución" in a two-column grid) rather than one or the other — a material with only an entrega and nothing to return shows "Sin movimientos" (neutral, not "Pendiente") on the devolución side instead of implying there's an untramitted devolución that was never real. Each movement row shows "Registro SID DD/MM/YYYY HH:MM" (`Entrega.sid_completado_en`/`Devolucion.sid_completado_en`, set the moment that one checkbox is ticked) once checked. It also has the same día/mes date filter as "Todas las OT" (`hoyISO`/`mesActualISO`/`ultimoDiaDelMes`, shared from `lib/fechas.ts` — see the timezone gotcha below), but scoped to each *movimiento's own fecha*, not the OT's creation date — a pedido only shows if it has at least one entrega/devolución inside the selected range. The OT-level "Completado" vs "En proceso" badge is *computed*, not a separate action, and deliberately **ignores the date filter**: completado requires both that every one of the OT's (non-tinta) pedidos already qualifies for that tab (nothing still stuck at 0) **and** that every visible one has its checkbox marked, computed off the full per-OT history regardless of the currently-selected date range or the search box / Pendientes-Completados-Todos filter — otherwise the badge would flip depending on which day happens to be selected.
  - **"Ingresados" tab (2026-09-15)** is the one exception to "pedido-based": it groups `Devolucion` rows with `es_ingreso_produccion = true` **directly by `numero_ot`**, not by pedido — because an ingreso registered against a loose pendiente (`crear_pendiente_libre`, the "Registrar ingreso de LDPE-3" button — see above) has `ot_material_id = NULL` and therefore no row in `vista_consumo` at all, so before this tab existed those SID trámites were **completely invisible** anywhere in Registro SID (confirmed against real data: OTs 77777, 8888 and 159 each had loose-pendiente ingresos with `sid_completado = false` and no screen showing them). This needed `numero_ot`/`cliente`/`unidad` added to `DevolucionOut` (`devoluciones_view.py`'s `_serializar`, resolved via `devolucion.ot_material.ot_proceso.ot` or `devolucion.ot_material_pendiente.ot`, whichever is set) since neither was previously exposed there. Within each OT's card, rows are grouped by `material_id` (not by pedido, since a loose one doesn't have one) and reuse the same `SeccionSid`/`MovimientoRow` components; a row with `ot_material_id == null` gets a small "ingreso almacén · sin registro de entrega" badge so it's obvious this material is still sitting as an unpromoted pendiente. This tab is purely additive — an ingreso already attached to a real pedido still also shows under Devueltos/Todos as before, don't remove that.

### Access control (usuarios, roles, módulos restringidos)

- `Usuario.rol` is `'admin'` or `'personal'` (default). **`admin` sees and uses everything, no exceptions.** `personal` starts with access to every module too — restriction is opt-in per module via `UsuarioModuloRestringido` rows, never the other way around (no row = full access). Don't invert this default.
- `security.requiere_modulo(modulo)` is the FastAPI dependency that gates a specific action: an `admin` always passes; a `personal` passes unless that exact `modulo` string is in their restricted set. `security.MODULOS_RESTRINGIBLES` (`crear_ot`, `registrar_entrega`, `registrar_devolucion`, `registro_sid`, `materiales`, `maquinas`, `excel_oc_mp`) must stay in sync with whatever `Usuarios.tsx` offers as togglable modules on the frontend — it's duplicated by hand, not derived from one shared source.
- Deliberately **not gated**: read-only `GET`s of data shared across screens (e.g. catálogos, `/consumo`) — the restriction model is about which actions/screens a `personal` user can act in, not about hiding shared data.
- The whole `/usuarios` router (`usuarios_view.py`) is gated behind `security.requiere_admin`, not `requiere_modulo` — there is no "personal with usuarios access" case, it's admin-only end to end. `Usuarios.tsx` (admin-only nav item) is where an admin creates/edits usuarios, toggles their módulos restringidos, and resets a password (`PUT /usuarios/{id}/password`) — there's no self-service "change my own password" endpoint, only an admin resetting someone else's. `scripts/set_password.py <INICIAL>` is the CLI equivalent for when no admin account can log in yet.

### Deployment topology and auto-update

The plant's real deployment (as of 2026-09) is 5 machines: the backend + PostgreSQL run on **one server PC on planta baja**; `OC_2025_bas_PRUEBA.xlsx` lives on the **jefe de área's PC on piso 1**, shared over the LAN (SMB); the other 4 PCs are stations running only the Electron app.

- **The Excel write-back still only needs to run on the server**, per the COM constraint documented above — moving the `.xlsx` file itself to a different machine doesn't change that. Microsoft Excel has to be installed **on the server**, and `ruta_excel_oc_mp` has to be a UNC path (`\\<pc-jefe>\<carpeta>\OC_2025_bas_PRUEBA.xlsx`), not a mapped drive letter (mapped drives are per-session and may not be visible to a service/scheduled-task context). The jefe's PC just needs the containing folder shared read/write.
- **Windows accounts on these machines are routinely non-admin**, which blocked or slowed down nearly every deploy step early on: opening the firewall for port 8000, enabling SMB/"File and Printer Sharing" inbound rules, `netplwiz` auto-login, creating a Scheduled Task with "run whether logged on or not", and enabling OpenSSH Server. Budget for needing someone with real admin credentials on-site for a batch of these at once rather than one at a time. `Set-ExecutionPolicy`/`Set-NetFirewallRule`/etc. all fail with a plain "Acceso denegado" (Win32 error 5) in a non-elevated PowerShell — that error means "open PowerShell as Administrator", not "the command is wrong".
  - Corollary: if PowerShell's script execution policy is locked down (common on a domain-joined machine, sometimes by Group Policy and not fixable even as admin), don't fight it — skip `.venv\Scripts\activate` entirely and call `.venv\Scripts\python.exe` / `.venv\Scripts\pip.exe` by full path for every command instead. Works identically, needs no policy change.
  - Corollary: after deciding **not** to set up `netplwiz` auto-login (rejected once already — plant pushback: an auto-logging-in PC reads as "no password" to anyone who has to explain it), don't leave a screen-lock startup script (`bloquear.bat`-style, dropped in the Startup folder to instantly re-lock after an auto-login) in place — it has no purpose without the auto-login it was designed to pair with, and just double-prompts every normal manual login. The two decisions travel together.
- **OpenSSH Server is now enabled on the server PC** (`ALMACEN-PC`, LAN IP `192.168.121.72`, account `zepol\Almacen`) — the IT supervisor did it, since it needs an elevated PowerShell the deploy account doesn't have (same blocker as the rest of this list). It's reachable **only from inside the plant LAN**; there's no port-forward or VPN, and none should be added just to publish updates remotely — see "Publishing a new version" above, a LAN-only share/`scp` is the right tool for that, not exposing SSH to the internet. From a dev machine that already has a key in the server's `authorized_keys`: `ssh <alias>` (key-based, no password — Windows OpenSSH won't accept a piped/non-interactive password prompt, so an automation session needs a key, not the account password). Two things that bite over that session specifically:
  - **The `Almacen` account is not a Windows administrator**, so anything CIM/WMI-backed fails with "No se puede conectar al servidor CIM. Acceso denegado" — this includes `Get-ScheduledTask`, `Get-NetTCPConnection`, and even plain `tasklist`. Use the non-CIM equivalents instead: `Get-Process`, `netstat -ano | findstr :8000`, `schtasks /query`.
  - **Restarting the backend after a `git pull`**: the Scheduled Task **"Zepol Backend"** (`iniciar_backend_oculto.vbs` → `iniciar_backend.bat` → `uvicorn`, on-logon trigger, "Solo interactivo", runs as `Almacen`) can be re-triggered from this SSH session with `schtasks /run /tn "Zepol Backend"` even though it's marked interactive-only. It normally spawns **two** python processes; only one ends up holding port 8000 — the other fails to bind and exits on its own, so it's safe to `schtasks /run` *before* killing the old process to confirm the mechanism still works, then `Stop-Process` the old PID(s) and `schtasks /run` again for the real restart. Check for a running `EXCEL.EXE` first if `escribir_oc_mp` might be mid-`Save()` (see the COM-kill gotcha above) — verify the restart with `GET /health`, not just "the command didn't error".
- **This server was found running with no `.env` file at all** (2026-09-08) — not missing a few keys, the file didn't exist, and no equivalent environment variables were set at the user or machine level either. `database.py`/`security.py` silently fall back to their hardcoded defaults in that case, which means `SECRET_KEY` was `"dev-secret-change-me"` — the literal string in this **public** repo — on a machine reachable over the LAN. That's a forgeable-admin-token situation for anyone who can reach port 8000, not just a "should rotate this someday" item. If you ever find a deploy machine behaving oddly around auth, or are setting one up fresh, check for `.env`'s *existence* before debugging further — `INSTALACION_SERVIDOR.md`'s step for generating a real `SECRET_KEY` is easy to skip past without erroring, since the app runs fine either way.
- **Auto-update**: `frontend/src/main/index.ts` wires `electron-updater` (`iniciarAutoUpdate`, called after `createWindow()`) with the **generic** provider, and reads the feed URL from the same `config.json`/`apiBaseUrl` every station already has (`${apiBaseUrl}/updates/`) — deliberately not a URL baked into the build, so one build works for every station regardless of which LAN it points at. `electron-log` is wired in as `autoUpdater.logger` specifically because a packaged Electron app has no visible console — without it there is no way to see why a check/download failed short of rebuilding with print statements; check `%APPDATA%/<app>/logs/main.log` first when auto-update misbehaves. The backend (`main.py`) mounts `StaticFiles` at `/updates`, backed by `sistema-mp/backend/updates/` (created on startup if missing, gitignored — binaries never go in git).
  - **Manual "Buscar actualización" button (added 2026-09-15), on the Login screen** — the automatic check (on launch + hourly) already existed, but staff wanted to trigger it themselves on their own schedule (e.g. right before copying a new build out) instead of waiting. `main/index.ts`'s `buscarActualizacionManual()` wraps `autoUpdater.checkForUpdates()` in a `Promise` racing one-time `update-available`/`update-not-available`/`error` listeners (removed via `.once`/`removeListener` regardless of outcome, so they never pile up across repeated clicks) and resolves a small tagged union (`sin-actualizacion` | `descargando` | `error`) instead of leaning on electron-updater's own resolved value, which isn't reliable for "was there actually something newer" across versions. Exposed as `ipcMain.handle('updates:buscar', ...)` → `window.api.buscarActualizacion()` (preload) → a plain button + status text in `Login.tsx` (visible before login, so it works for whoever's at the station regardless of who logs in). `autoDownload` stays `true` (see below) — this button only triggers the *check*; if something's found it downloads itself in the background exactly like the automatic path does, and the existing "lista para instalar" dialog (`update-downloaded`) is what actually prompts to restart. In dev (`!app.isPackaged`) it resolves an `error` immediately with an explanatory message instead of calling into electron-updater, which isn't meaningful against an unpackaged app.
  - **Publishing a new version**: bump `"version"` in `frontend/package.json`, `npm run dist`, then copy all **three** generated files (`<Product> Setup <version>.exe`, the matching `.exe.blockmap`, and `latest.yml`) into `sistema-mp/backend/updates/` on the server, replacing what's there. All three are required — `latest.yml` is what electron-updater actually reads to decide if a newer version exists, and the `.blockmap` is what lets it download a delta instead of the full installer next time. No backend restart needed; it's served as a static file. Stations pick it up on next launch or within the hourly re-check.
  - **The installer must stay per-user — NSIS `oneClick` with `perMachine` unset.** That's electron-builder's default and `package.json` deliberately doesn't override it: a per-user install lands in `%LOCALAPPDATA%\Programs` and updates itself with **no elevation prompt**. Setting `perMachine: true` would install into `Program Files` and make every auto-update ask for admin credentials the plant accounts don't have (see the non-admin note above) — silently breaking the update path on all 5 stations at once, and only discoverable by watching a station fail to update. Verified against `dist/builder-debug.yml` (it includes `oneClick.nsh`).
  - `build.publish.url` in `package.json` is hardcoded to `http://localhost:8000/updates/` and is **not** what the stations read — `revisarActualizaciones()` overrides it at runtime through `setFeedURL` with each station's own `apiBaseUrl`. The baked-in value only matters for `electron-builder --publish`, which this project never runs. Don't "fix" it to a real server IP thinking that's what points the stations somewhere; that would just re-hardcode the thing the runtime lookup exists to avoid.
  - Getting the 3 files onto the server without SSH set up means round-tripping through a USB/external drive — tedious but works. **SSH is now set up on this server** (see the SSH bullet above), so publishing is a single `scp ... zepol:.../sistema-mp/backend/updates/` from a machine with a key already installed — no more USB.
  - **Gotcha that has already caused a real, hours-long bug hunt**: local commits sitting unpushed. `git push` is a separate, explicit step from `git commit` (see CLAUDE.md's own git-safety rules) — it's easy to accumulate several real commits locally (including actual bug fixes) without ever pushing them, and a `git clone`/`git pull` on another machine (the server) then silently gets the **older, buggy** code with no error. This is exactly how the `excel_oc_mp._abrir_hoja` seek bug (already fixed and committed locally on 2026-09-01) reappeared on a fresh server clone on 2026-09-03 — the fix was sitting 6 commits ahead of `origin/main`, unpushed, the whole time. Before trusting a deploy machine's behavior as "the current code", check `git log --oneline -3` there against what you expect, and on the dev side run `git status --short --branch` (look for "ahead N") before signing off that something "is already fixed" — fixed locally isn't fixed anywhere else until it's pushed **and** pulled.
  - **Same failure mode, different cause — a source file silently excluded by `.gitignore`.** The root `.gitignore` is the standard Python template, whose `lib/`, `build/`, `var/`, `target/`, `parts/` and `env/` entries are **unanchored**, so they match at *any* depth, not just the repo root. `lib/` was therefore swallowing `sistema-mp/frontend/src/renderer/src/lib/` — real frontend source. It stayed invisible because `.gitignore` doesn't affect already-tracked files: `api.ts`, `AuthContext.tsx` and friends kept showing up in `git status` as normal, and only a **newly added** file in that folder was dropped, without warning, from `git add`/`git status`. The commit and push both look fine; the server clone then fails to build with an unresolvable import. `lib/`/`lib64/` are now anchored as `/lib/`, `/lib64/` — if you add a source folder named after any of the other unanchored entries above, anchor that one too. Cheap check after creating a new source file: `git status --short` should list it as `??`; if it doesn't, run `git check-ignore -v <path>` to see which rule ate it.
  - Related gotcha: after killing a stray backend process to force a restart with new code, verify there isn't a **second** `python.exe` still bound to port 8000 from a different Python install (e.g. the venv's vs. a system-wide `Python312` install both having been used to launch `uvicorn` at different points) — `Get-CimInstance Win32_Process -Filter "Name = 'python.exe'"` can show two, and only one of them owns the port. `Get-NetTCPConnection -LocalPort 8000 -State Listen | Select OwningProcess` tells you which PID is actually being hit before you waste time debugging "the fix isn't working" against the wrong process.
- The repo (`EliasDevOps-alt/ZEPOL-ltda.-`) is currently **public** on GitHub — worth knowing before assuming a token is needed for anything (e.g. GitHub Releases as an alternative update channel would work without embedding credentials), and worth flagging to the user if this business logic being world-readable is unintentional.
- `sistema-mp/backend/scripts/iniciar_backend.bat` (cd's to the backend dir so `load_dotenv()` finds `.env`, then runs `uvicorn` via the venv's `python.exe` — used as the Scheduled Task's action, launched hidden via a small `.vbs` wrapper so no console window lingers on screen) and `restaurar_db_servidor.bat` (recreates `zepol_mp` from a `pg_dump -F c` file dropped next to it — idempotent, safe to re-run) exist to make the runbook copy-pasteable instead of freehand every time.

### Styling

Color tokens are Tailwind v4 `@theme` variables in `src/renderer/src/index.css` — no `tailwind.config.js`. The palette is fixed light-only on purpose (no `prefers-color-scheme` dark variant): this is a shop-floor app used by non-technical operators on shared PCs, and it must not silently go dark based on whichever Windows theme a given station happens to have. `--color-primary` is the cyan from the ZEPOL logo; `--color-accent-*` are the logo's decorative circle colors (used sparingly, e.g. the login card's top gradient bar); `success`/`warning`/`destructive` are semantic status colors, not brand colors — use them by meaning (COMPLETO/PARCIAL/error), not decoratively.
